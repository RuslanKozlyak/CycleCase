# Задание: постройте велосипедный маршрут по популярным улицам

Подберите и настройте модель, которая по характеристикам улиц строит велосипедные маршруты,
согласующиеся с наблюдаемой популярностью поездок. Основной набор — дорожная сеть Констанца и
агрегированные потоки STADTRADELN по участкам улиц. Сравните результат с кратчайшим путём:
насколько популярные улицы выбирает модель и насколько увеличивает длину маршрута.

Популярность маршрута здесь — показатель популярности составляющих его улиц. Данные Констанца
не содержат целых индивидуальных поездок между A и B. Личные GPX Петербурга используются для
дополнительной проверки переноса модели без перенастройки.

## Что вам дано

`prepare_city(city, cache_dir=...)` возвращает две GeoDataFrame:

- `edges` — одно направленное ребро улицы в каждой строке;
- `nodes` — узлы графа с координатами.

В `edges` есть идентификаторы `u`, `v`, `key`, длина `length_m`, геометрия и OSM-признаки:
`highway`, `surface`, `smoothness`, `cycleway`, `bicycle`, `lit`, `service`, `access`, `maxspeed`,
`lanes`, `width`, `oneway`. Категории — строки с разделителем `;`, числа — `float` с `NaN`, флаг
`oneway` — `bool`. В ячейках нет списков и словарей.

Наблюдаемая популярность улиц намеренно скрыта от алгоритма: она лежит в отдельном
`popularity.parquet` и используется функцией `score`. Подглядывать в неё при построении стоимости
нельзя — это целевая переменная, по которой оценивается маршрут.

Количество известно не для всех рёбер: `trips=NaN` — нет сопоставленного наблюдения,
`trips=0` — подтверждённый ноль, `has_observation` — признак наличия измерения.
Не удаляйте дорогу из сети из-за отсутствия поездок. При обучении и оценке используйте только
известные метки и явно показывайте покрытие маршрута измерениями; не заменяйте NaN нулями.

Для ML разрешено использовать популярность **только обучающей части train** как целевую переменную.
Веса модели и силу её влияния выбирайте на validation; test открывается после выбора настроек.
При построении маршрута модель получает только OSM-признаки и возвращает прогноз, а поиск —
стоимости рёбер. Наблюдаемую популярность validation/test нельзя подставлять в стоимость.

Поддерживаются два набора данных:

- `konstanz` — потоки STADTRADELN;
- `saint_petersburg` — личные GPX-треки.

## Пайплайн

```text
prepare_city() -> edges, nodes
edges -> ваша pandas-маска -> check_connectivity()
      -> build_graph(edges, nodes, cost=ваша_функция)
      -> find_route(..., search=алгоритм, turns=модель_поворотов)
      -> score(routes, city)
```

Начните с готового примера:

```python
edges, nodes = prepare_city("konstanz", cache_dir=CACHE_DIR)
filtered = filter_edges(edges, is_rideable, keep_largest=True)

graph = build_graph(filtered, nodes, cost=default_comfort)
route = find_route(graph, origin, destination)
```

## Обязательная часть

1. Изучите данные: покажите `value_counts` важных тегов и долю заполненных значений.
2. Напишите фильтр `keep(edges) -> Series[bool]`. Проверьте связность после фильтрации. Объясните,
   почему удаляете каждую категорию дорог.
3. Напишите векторную функцию `cost(edges) -> Series`. Значения должны быть конечными и строго
   положительными; единица измерения — эквивалентные метры.
4. Постройте маршруты для тех же пар начала/конца, что и базовые модели.
5. Сравните результат через `score`, карту и несколько конкретных примеров. Не выбирайте веса по
   тестовым значениям популярности.

Простейшая функция стоимости:

```python
def my_cost(edges):
    factor = 1.0 + 2.0 * edges["highway"].eq("primary")
    factor += 0.5 * edges["surface"].isin(["sett", "cobblestone"])
    return edges["length_m"] * factor
```

- Замените `nx.dijkstra_path` другим алгоритмом networkx (`nx.astar_path`) или своим.

- Дополнительно перенесите выбранную модель Констанца на личные GPX Петербурга без перенастройки.

## Правила интерфейсов

- Фильтр получает всю таблицу и возвращает булеву Series с тем же индексом.
- Стоимость получает всю таблицу и возвращает Series той же длины и с тем же индексом.
- Поиск получает только минимальный граф: `cost`, `length_m`, `geometry` и идентификаторы рёбер.
- Ни фильтр, ни стоимость, ни поиск не читают `popularity.parquet`.
- Не меняйте `score`: это общий чёрный ящик для сравнения решений.

Готовые `is_rideable`, `default_comfort`, восемь `COMFORT_PRESETS`, `nx.dijkstra_path` и
`TurnConfig` — примеры и baseline. Их можно копировать и изменять через те же публичные интерфейсы.

## Метрики

`score` показывает объезд относительно кратчайшего пути, число поворотов, использование популярных
улиц/личных треков, сумму наблюдаемых поездок по всем пройденным рёбрам, долю крупных улиц и число
проблемных рёбер. Повторное использование ребра в разных OD-маршрутах учитывается повторно.
Основной критерий — наблюдаемая популярность улиц вдоль маршрута при ограничении объезда.
В ML-разделе она считается как среднее `log(1 + trips)`, взвешенное по длине оценённых участков;
влияние настроек проверяется на одинаковых OD-парах. Сумму поездок не используйте как главный
критерий: она зависит от длины и разбиения дороги на рёбра. Остальные метрики помогают объяснить
компромисс и убедиться, что популярность не достигается за счёт неприемлемого объезда.
