# Задание агенту: перевести проект на табличный пайплайн

Проект — учебный, для хакатона школьников. Цель этой работы: сделать данные явными и удобными
(плоская таблица рёбер), а все места, которые студенты будут переписывать, — сменными функциями.

## Целевая схема

```
prepare_city()      →  edges, nodes        подготовка: скачивание OSM, привязка поездок, раскладка тегов
   (скрыто)            GeoDataFrame        кешируется; студент сюда не заглядывает

edges  →  фильтрация pandas  →  check_connectivity()  →  build_graph(edges, nodes, cost)
                                                             ↓
                                                      find_route(G, ..., search, turns)
                                                             ↓
                                                        score(route, city)   ← чёрный ящик
```

Студент пишет: маску фильтра, функцию комфорта, при желании — алгоритм поиска и модель поворотов.
Всё остальное готово.

## Инварианты

1. **Популярность (`stad_trips`, `gpx_tracks`) не лежит в таблице рёбер и не попадает в граф.**
   Её видит только `score` и функции визуализации/корреляции. Сейчас `stad_trips` пишется прямо в
   рёбра графа — это надо убрать.
2. **Таблица рёбер плоская.** Никаких списков, множеств и вложенных структур в ячейках.
   Категориальные признаки — строки, числовые — float с `NaN`, флаги — bool.
3. **Сменные точки не ломают остальное.** Замена фильтра, функции комфорта, алгоритма поиска или
   модели поворотов не требует правок в метриках, картах и кеше.
4. **Ноутбук остаётся тонким:** параметры, вызовы, отображение.
5. Числовые результаты после рефакторинга должны совпасть с текущими (см. «Приёмка»).

## Что уже есть

| модуль | содержимое | судьба |
|---|---|---|
| `data.py` | загрузка STADTRADELN и GPX | без изменений |
| `graph.py` | скачивание OSM (`network_type="all"`), кеш GraphML, фильтр `is_rideable`, проекция | переезжает внутрь `prepare_city` |
| `matching.py` | привязка поездок и GPX к рёбрам | результат уходит в отдельную таблицу, не в граф |
| `comfort.py` | 10 множителей, `comfort_feature_table`, `add_comfort_cost` | таблица становится источником, `add_comfort_cost` заменяется векторной функцией |
| `routing.py` | `dijkstra`, `dijkstra_turns`, `count_turns`, `build_routes`, кеш маршрутов | граф теперь приходит из `build_graph`; интерфейс поиска сохранить |
| `evaluation.py` | метрики по маршрутам | становится внутренностями `score` |
| `visualization.py` | карта 2×2 | принимает `edges` вместо графа с тегами |
| `config.py` | `COMFORT_PRESETS`, `TurnConfig`, `GraphConfig` | пресеты становятся готовыми функциями комфорта |

## Что не удалять

Нынешние реализации — это **эталон и тестовый материал**. Ничего из них не выбрасывать: перевести на
новый пайплайн и оставить в том виде, в каком их подключил бы студент.

- **Пресеты** (`COMFORT_PRESETS`, все 8) остаются. Каждый становится обычной функцией комфорта,
  подставляемой через тот же публичный интерфейс, что и студенческая: `build_graph(edges, nodes,
  cost=preset["cost"])`. Никаких внутренних привилегий у них быть не должно.
- **`default_comfort` с таблицей весов** остаётся как «референсная реализация», на которую студенты
  смотрят и которую копируют.
- **`is_rideable`** остаётся как пример фильтра и как значение по умолчанию.
- **`dijkstra`, `dijkstra_turns`, `TurnConfig`, `count_turns`** остаются как готовые реализации поиска
  и модели поворотов.
- **Скалярный `comfort_components`** остаётся для таблицы объяснений признаков.

Смысл в том, что эти реализации проходят по новому пайплайну **как чужой код**: если что-то из них
подключается только благодаря доступу к внутренностям, интерфейс дырявый и его надо чинить. Заодно
они дают baseline, с которым сравниваются студенческие решения, и материал для тестов.

Удалять можно только то, что после перехода физически некому вызвать (например, запись `stad_trips`
в рёбра графа). Всё остальное, что кажется лишним, — выносить в примеры, а не стирать.

## Что сделать

### 1. `preparation.py` — подготовка данных

```python
def prepare_city(city: str, *, cache_dir: Path, refresh: bool = False) -> tuple[gpd.GeoDataFrame, gpd.GeoDataFrame]:
    """Скачать OSM, привязать наблюдения, вернуть (edges, nodes). Кеш — GeoParquet."""
```

- Города описываются в одном месте (`CITIES`): bbox или центр+радиус, CRS, источник наблюдений.
- Внутри: скачивание графа (как сейчас), `is_rideable` как базовый фильтр непроезжего,
  привязка STADTRADELN / GPX, раскладка тегов по колонкам.
- **Схема `edges`** (ровно эти колонки, в этом порядке):

  | колонка | тип | примечание |
  |---|---|---|
  | `u`, `v`, `key` | int64 | |
  | `length_m` | float64 | |
  | `highway`, `surface`, `smoothness`, `cycleway`, `bicycle`, `lit`, `service` | string | несколько значений склеить через `;`, пусто → `NA` |
  | `maxspeed`, `lanes`, `width` | float64 | `NaN`, если тега нет |
  | `oneway` | bool | |
  | `geometry` | LineString | метрическая CRS |

- **Схема `nodes`:** `node` (int64), `x`, `y` (float64), `geometry` (Point).
- **Наблюдения в отдельный файл** `popularity.parquet`: `u`, `v`, `key`, `trips`. Его читает только
  `score` и функции карт/корреляций.
- Кеш: `<cache_dir>/<city>/edges.parquet`, `nodes.parquet`, `popularity.parquet` плюс сырой GraphML.
  Ключ кеша включает список тегов и версию схемы.

### 2. `check_connectivity` — контроль после фильтрации

```python
def check_connectivity(edges, nodes, *, keep_largest: bool = False, report: bool = True) -> gpd.GeoDataFrame:
    """Сколько компонент осталось, какие рёбра были перемычками; при keep_largest — вернуть крупнейшую."""
```

- Считает слабые компоненты, печатает: число компонент, размер крупнейшей, сколько рёбер и километров
  отвалилось.
- Ищет и показывает 3–5 примеров «перемычек»: рёбра, удаление которых увеличило число компонент
  (сравнение с нефильтрованным набором).
- Делает и предупреждение, и обрезку: без `keep_largest` только предупреждает.

### 3. `build_graph` — таблица → граф

```python
def build_graph(edges, nodes, cost) -> nx.MultiDiGraph:
    """cost: Callable[[gpd.GeoDataFrame], pd.Series] | pd.Series | str. Вес ребра — 'cost', метры."""
```

- Векторная функция комфорта: на входе вся таблица, на выходе `Series` той же длины.
- На рёбра графа кладутся только `cost`, `length_m`, `geometry` и идентификаторы — **не теги**.
- Проверки на входе: положительная стоимость, отсутствие `NaN`, совпадение длины.

### 4. Функции комфорта вместо конфигов

- Базовая: `default_comfort(edges, config=DEFAULT_COMFORT_CONFIG) -> pd.Series`, векторная,
  воспроизводит текущие 10 множителей.
- `COMFORT_PRESETS` остаются, но каждый пресет — это `{label, description, cost, turns, search}`,
  где `cost` — функция.
- Скалярный путь (`comfort_components` по одному ребру) оставить только для таблицы объяснений
  признаков: она полезна студентам и в отладке.

### 5. `find_route` и `score`

```python
def find_route(graph, origin, destination, *, search=dijkstra_turns, turns=TurnConfig()) -> dict
def score(routes, city, *, cache_dir) -> pd.DataFrame
```

- `find_route` — тонкая обёртка над нынешним `route_record`; `build_routes` остаётся для пакетного
  прогона по пресетам вместе с кешем.
- `score` читает `popularity.parquet` и считает: популярность, долю популярных улиц, долю «плохих»
  рёбер (лестницы, шоссе, частная территория — по списку правил), объезд к кратчайшему, повороты.
  Внутри — нынешние `evaluate_corridor_popularity` и `compare_route_models`.

- Переписать `TASK.md` в задание для студентов (постановка, данные, пайплайн, правила, метрики,
  идеи, критерии) — текст прошлой версии этого файла годится за основу.
- README: новая схема пайплайна и точки расширения.

## Порядок работ

1. `preparation.py` + схемы + кеш; убрать `stad_trips` из графа.
2. `check_connectivity` + тесты.
3. `build_graph` + векторный `default_comfort`; пресеты на функции.
4. `find_route` / `score`; перенос метрик.
5. Ноутбук, README, задание для студентов.

Каждый шаг заканчивается зелёными тестами; ноутбук прогоняется целиком после шагов 3 и 5.

## Тесты, которые должны появиться

- таблица рёбер: плоские типы, нет колонок популярности, число рёбер совпадает с графом;
- `check_connectivity`: фильтр, разрывающий связность, даёт предупреждение и правильную перемычку;
  `keep_largest` оставляет крупнейшую компоненту;
- `build_graph`: вес равен значению функции комфорта; отрицательная или `NaN`-стоимость — ошибка;
- функция комфорта: векторная и скалярная реализации дают одинаковый результат на одних данных;
- `score`: метрики не зависят от того, есть ли популярность в `edges` (её там быть не должно).

## Приёмка

1. `pytest` зелёный.
2. Ноутбук прогоняется целиком без ошибок.
3. Итоговые таблицы Konstanz и Санкт-Петербурга совпадают с сохранёнными эталонами
   (`outputs/konstanz_presets.csv`, `outputs/spb_presets.csv`) с точностью до 1e-6; расхождения
   объяснены.
4. В `edges.parquet` нет ни одной колонки, производной от поездок.
5. Замена функции комфорта, алгоритма поиска и модели поворотов работает без правок в других модулях
   (проверяется тестами).
6. Все 8 пресетов, `is_rideable` и обе реализации поиска подключены через публичный интерфейс и дают
   те же маршруты, что раньше. Ни одна из них не обращается к внутренностям пайплайна.

## Ограничения и риски

- **Размер СПб:** 360 тысяч рёбер. Сборка графа из таблицы должна быть векторной, поиск с поворотами
  на таком графе идёт секунды; кеш маршрутов сохранить.
- **Инвалидация кеша:** ключ должен включать схему таблицы, список тегов, веса, повороты и алгоритм.
- **Не ломать оговорки в коде:** запрет на популярность в признаках — это инвариант, а не пожелание.
- **Открытый вопрос:** вес тротуаров (`highway=footway`) по умолчанию. Сейчас 1.3, и из-за этого
  маршруты в СПб уходят с проспектов на тротуары. Решить до финального прогона.
